Temporal を初めて使う Go エンジニア向けに、docs/design.md を読む前の地図として7枚の図を並べました。文は最小限で、図に描いた事実は末尾の出典（Temporal 公式ドキュメント）で確認しています。各図の下の緑の欄が、その概念がこのリポジトリのどこに出てくるかです。

1全体像

Temporal Server はあなたのコードを一切実行しません。Server は Task Queue に Task を置き、Event History を永続化するだけで、Worker が Task を取りに行き、Workflow と Activity を自分のプロセスで走らせて結果を返します。

矢印の向きに注意してください。Worker → Server の実線は Worker が同期 RPC で long poll している線で、Server から Worker へ押し込む経路はありません。だから Worker は受信ポートを開けず、DNS 登録もいりません。

このリポジトリでは: 仕様スイートが プロセス内に dev server と Worker を両方立てて、Client として saga を開始する — specsteps/suite_test.go。Worker が登録する Workflow と Activity は example/order/。

2Task Queue と Worker の対応

Task Queue は登録不要で、名前を指定した瞬間に作られる軽い列です。実質的には「その名前を poll する Worker のグループ名」で、どの Task がどの Worker に渡るかは決まっていません。

C の形が、決済チームと在庫チームがそれぞれ自分のコードと資格情報だけを持つ Worker を運用するときの配線です。Workflow は注文チームの Worker で走り、Activity Task だけが他チームの Queue に置かれます。

このリポジトリでは: 今は全ステップが Workflow と同じ Queue で動く — example/order/workflow.go の TaskQueue。ステップごとに Task Queue を変えられるようにするのが次の変更で、C の形がその配線になる。

3Workflow と Activity の境界

Workflow 関数は同じ入力なら同じ順序で同じ Temporal API を呼ぶ必要があります（決定性）。外の世界に触ること、時刻や乱数のように実行ごとに変わることは、境界の右側か workflow パッケージの代替に寄せます。

このリポジトリでは: 判断は Workflow 側の saga.Func に、外部呼び出しは saga.Activity に置く — saga/step.go。Activity 側に求める冪等性の約束は docs/activity-contract.md。

41つの Activity の一生

1回の ExecuteActivity は1つの Activity Execution で、その中で Activity Task（＝1 attempt）が retry の回数だけ繰り返されます。4つの timeout のうち3つは attempt ごと、ScheduleToClose だけが全体を測ります。

StartToClose か ScheduleToClose のどちらかは必須で、既定はどちらも ∞ です。Worker が落ちて連絡が途絶えたとき Server が retry を起こす拠り所は StartToClose なので、公式はこちらを設定することを強く勧めています。

このリポジトリでは: Options.ActivityOptions と CompensationOptions はどちらかの timeout を必須にし、補償の ScheduleToCloseTimeout は残り予算に clamp する — saga/saga.go。example はすべて StartToCloseTimeout と MaximumAttempts: 1。

5Event History と Replay

Worker が Workflow Task を取ると、Workflow 関数を先頭から実行し直します。すでに History にある Activity の結果はそこから即座に返るので Activity は再実行されず、History の末尾に追いついたところから新しい Command を出します。

このリポジトリでは: 冪等キーが replay で同じ値になるよう KeyFunc は決定的でなければならず、既定は RunID + "/" + name — saga/saga.go。ステップの Activity と補償は同じ History の Event として残る。

6Workflow ID / Run ID / Activity ID

Workflow ID はあなたが決める業務識別子（注文番号など）で、Namespace の中で Open な実行について一意です。Run ID は Temporal が振る実行の識別子で、Retry・ContinueAsNew・Cron・Reset のたびに新しい Run が同じ Workflow ID の下に連なります。

このリポジトリでは: Activity ID にこのライブラリが冪等キーを載せる — saga/step.go。キーの既定が RunID + "/" + name なのは、Retry や ContinueAsNew で別 Run になったら別のキーにするため（FirstRunID は Run をまたいで同じなので使わない） — saga/saga.go。子ワークフローでは同じキーを Workflow ID に載せる — saga/key.go。

7Signal / Query / Update と Child Workflow

走っている Workflow に外から働きかける手段は3つで、違いは方向と、History に残るかどうかです。Workflow が別の Workflow を子として起動することもでき、子は自分の History と、必要なら別の Task Queue を持ちます。

このリポジトリでは: signal 待ちを1ステップにする saga.AwaitSignal — saga/signal.go、example/approval/。子ワークフローをステップにする saga.ChildWorkflow — example/childflow/。Workflow から別の Workflow へ signal を送るステップ — example/external/（Query も HeldQuery として使う）。
