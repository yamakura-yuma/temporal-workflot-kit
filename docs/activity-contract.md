# アクティビティ側に必要なこと

`saga.Step` は forward と補償の両方に同じ冪等キーを渡します。アクティビティ側の仕事は、
**そのキーで重複実行を止めること**と、**取り消すものが無いときに補償が成功すること**の
2つです。

1つ目は、**副作用がどこに行くか**で3つの場合に分かれます。どれに当たるかで、書く量が
変わります。簡単なほうから順に書きます。

| | 副作用の行き先 | 鍵をどこに置くか | 別の台帳 |
| --- | --- | --- | --- |
| 場合1 | 自分の DB | 業務行の UNIQUE 列 | 要らない |
| 場合2 | 冪等キーを受け取る外部 API | 下流が持つ | 要らない |
| 場合3 | 冪等キーを受け取らない外部 API | 自分で用意した store | 要る |

**別の台帳が要るのは場合3だけです。** 場合1と場合2では、鍵を置く場所が既にあります。

## 場合1 — 自分の DB に書く（一番多い）

在庫を押さえる、注文行を立てる、伝票を起こす。副作用が自分の DB への書き込みなら、
**冪等キーをその業務行の UNIQUE 列にします。**

```sql
INSERT INTO reservations (id, order_id, idem_key)
VALUES (?, ?, ?)
ON CONFLICT (idem_key) DO NOTHING
RETURNING id;
```

```go
func (a *Activities) Reserve(ctx context.Context, req ReserveReq) (string, error) {
    k, _ := saga.IdempotencyKey(ctx)
    return a.db.InsertReservation(ctx, req.Order.ID, k)   // 既にあれば既存の id が返る
}
```

この1文が、**仕事をすることと鍵を claim することの両方を兼ねています。** 2回目の実行は
`ON CONFLICT` で弾かれ、既にある行の id が返ります。

だから**別の台帳は要りません。行そのものが台帳です。** 「この鍵はもう使ったか」は「この
鍵の行があるか」と同じことなので、2つ持つ理由がありません。

後始末も要りません。書き込みと仕事が同じ1操作なので、失敗したときに鍵を release する
段取りがそもそも無く、**行が無いだけ**です。場合3のように「claim はしたが仕事はしなかった」
という中途半端な状態が作れません。

## 場合2 — 外部 API が冪等キーを受け取る

決済 API の `Idempotency-Key` ヘッダのように、下流が自分で重複排除してくれるなら、
`saga.IdempotencyKey(ctx)` で取ったキーをそのまま渡すだけです。

```go
func (a *Activities) Charge(ctx context.Context, req ChargeReq) (string, error) {
    k, _ := saga.IdempotencyKey(ctx)
    return a.gateway.Charge(ctx, k, req.Order.Amount)   // k が下流の重複排除キー
}
```

**アクティビティ側に持つ状態はありません。** 2回目の呼び出しは下流が弾き、1回目と同じ
結果が返ります。リトライしてもタイムアウト後に2つの試行が重なっても、課金は1回です。

下流がキーを受け取るなら、これ以上のことをする必要はありません。台帳を持つのは、下流が
やってくれないぶんを肩代わりするからです。

## 場合3 — 外部 API が冪等キーを受け取らない（一番厄介）

下流が同じリクエストを2回受ければ2回実行し、しかも自分の DB に書くわけでもない。
ここで初めて、**業務データとは別の store に鍵を先に claim してから呼ぶ**段取りが要ります。

段取りはこうです。

1. 鍵を claim する。取れなければ先行した試行がいるので、その結果を返す
2. 下流を呼ぶ
3. 失敗したら claim を release する。しないと、後続のリトライが全部「もう済んでいる」と
   誤判定します

ここで**キーが使用済みか確認してから処理する形では足りません**。タイムアウトすると2つの
試行が同時に走り、両方が「未使用」を見ます。

```go
// これでは二重課金する
k, _ := saga.IdempotencyKey(ctx)
if charged(k) {
    return cached(k), nil   // ← check
}
return gateway.Charge(req)  // ← act
```

必要なのは一意制約つきの claim です。確認と書き込みが1つの原子的な操作になっていて、
勝者が1つだけ決まる形にします。

```sql
INSERT INTO ops(key, state) VALUES (?, 'CHARGING')
ON CONFLICT (key) DO NOTHING
RETURNING state;
```

場合1と同じ `ON CONFLICT` ですが、**入る先が違います。** 場合1では業務行そのものに入って
いて、ここでは業務データの外にある鍵専用のテーブルに入っています。その分離があるせいで、
claim と実際の仕事の間が開き、3番目の release が要る。この節が一番長いのはそのためです。

行が返れば自分が勝者なので処理に進み、返らなければ先行した試行がいるので、その結果を
返します。ストレージが変われば書き方も変わりますが、**確認と書き込みの間に他の試行が
割り込めないこと**が要件で、そこは変わりません。

## どの場合でも — 補償は、取り消すものが無いときに成功する

補償は処理が起きる前に登録されるので、実際には起きなかったステップに対しても呼ばれます。
そこでエラーを返すと、ロールバック全体が失敗扱いになります。

判定の材料は、forward が鍵をどこに置いたかで決まります。

**場合1** — 業務行を消す（あるいは取り消し済みにする）だけです。消えた行が0なら、そもそも
何も起きていなかったということなので、成功を返します。

```go
func (a *Activities) Unreserve(ctx context.Context, req ReserveReq) error {
    k, _ := saga.IdempotencyKey(ctx)
    _, err := a.db.DeleteReservation(ctx, k)   // 行が無ければ 0 行削除。それも成功
    return err
}
```

**場合2** — **補償も下流に鍵を渡すだけ**で済むことが多くなります。取り消す対象があったか
どうかを知っているのは下流で、「そんな課金は無い」を成功として扱えるかも下流の API 次第
だからです。

```go
func (a *Activities) Refund(ctx context.Context, req ChargeReq) error {
    k, _ := saga.IdempotencyKey(ctx)
    return a.gateway.RefundByIdempotencyKey(ctx, k)   // 対象が無ければ成功を返す API
}
```

下流が「対象が無い」を 404 で返すなら、そこだけは自分で吸ってください。**成功に変換する
のはこの1点だけ**で、それ以外のエラーはそのまま返します。潰しすぎると、本当に返金できて
いないのに成功したことになります。

**場合3** — 台帳からその鍵の claim を落とせたかどうかがそのまま判定になります。

```go
func (a *Activities) Refund(ctx context.Context, req ChargeReq) error {
    k, _ := saga.IdempotencyKey(ctx)
    if !a.release(k) {
        return nil   // 課金の記録が無い。返すものが無いので成功
    }
    return a.gateway.Refund(k)
}
```

## example の `Ledger` はどれか

**ここは読み違えやすいので、先に結論を書きます。`example/*/` の `Ledger` は場合3の段取りで
書かれていますが、example の下流は本来場合1に当たります。**

example の下流は自分のプロセス内の `map` です。外部 API ではなく自分のストアなので、素直に
当てはめれば場合1です。ところが `Ledger` は場合3の段取り、つまり**鍵を別の store に claim
してから実行し、失敗したら release する**形で書かれています。`Reserve` が
`a.claim(k, ...)` を呼び、失敗時に `a.release(k)` を呼んでいるのがそれです。

**つまり example は、一番多い形を、一番厄介な形の書き方で書いています。** これが「`Ledger`
が何のためにあるのか読み取れない」の直接の原因です。台帳は場合3のための道具なのに、場合3
ではない状況に置かれているので、何を肩代わりしているのかが見えません。

自分の DB に書くだけなら、上の `ON CONFLICT` 1文で済みます。**別の台帳は要りません。**
`Ledger` を読むときは、場合3の書き方の例として読んでください。自分のコードが場合1なら、
写す先は `Ledger` ではなく場合1の節です。

（example のコードは後続の別タスクで直します。）

## 塞げていないこと

**この節は場合2と場合3、つまり副作用が外部にある場合の話です。** とくに場合3で顕著に
なります。

補償は、取り消す対象が実際に起きたかどうかを確実には判定できません。タイムアウトした
forward はワーカー上で動き続けます。

```
t=0     Charge を StartToCloseTimeout=10s でスケジュール
t=0.1   ワーカー A が決済ゲートウェイに POST。応答待ち
t=10    サーバがタイムアウトを記録。ワーカー A は止まらない
t=10.1  補償フェーズが Refund を実行
t=10.2  Refund は課金の記録を見つけられず、契約どおり成功を返す
t=10.5  ワーカー A にゲートウェイから 200 が返り、課金レコードが書かれる
```

課金は通り、返金は「正しく」スキップされ、ワークフローは失敗で終わります。契約を完璧に
守った結果がこれです。

塞ぐには、補償がトゥームストーンを書いて forward がそれを見てからコミットする、つまり
両者が1つのストアで直列化されている必要があります。外部の決済ゲートウェイや配送キャリアが
相手なら無理です。ライブラリ側でできることはありません。

**場合1が3つの中で一番安全なのは、まさにここです。** forward も補償も同じ DB に入るので、
この直列化が実際に書けます（補償が取り消し済みの行を残し、forward が同じトランザクション
でそれを見てからコミットする）。副作用が外部にある場合2と場合3では、書きようがありません。

冪等キーを受け付けない下流も同じく安全にできません。送信済みのメールのように取り消せない
副作用も。

**ContinueAsNew すると、前の run で登録した補償は失われます。** `Saga` はその run のメモリ上に
あるだけで、履歴にも入力にも残りません。新しい run から前の run のステップを巻き戻す手段は
無いということです。

長い saga を ContinueAsNew で刻むなら、どこまで補償が必要かを自分で入力に載せて引き継ぐ
設計が要ります。`Run` は ContinueAsNew を「saga が続いているだけ」として扱い補償しないので、
そこで黙って取りこぼすことはありませんが、**引き継ぎは利用者側の仕事**です。

ワークフローは terminate ではなく cancel してください。terminate はワークフローコードを
一切実行しないので、何も補償されません。

それからこのパッケージは、ワークフローコマンドを発行します。バージョンを上げると、使って
いる全ワークフローのコマンド列が変わり、実行中の run のリプレイが壊れる。コマンドが
パッケージの内側にあるので、利用側は `workflow.GetVersion` で囲えません。実際のところ、
旧バージョンで始まった saga が尽きるまでバージョンは動かせません。コピーせず依存として
取るなら、ここは織り込んでおいてください。
