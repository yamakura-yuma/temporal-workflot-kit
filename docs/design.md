# なぜ 30 行で済ませないのか

Temporal の SDK に saga のヘルパーはありません（`saga` や `Compensat` で全文検索して
0件）。公式サンプルの `Compensations` はスライスと逆順ループで30行ほど。たいていは
それで足ります。

足りなくなるのは次の4点を踏んだときで、どれも異常系でしか表に出ません。このライブラリ
の中身は、実質この4つです。

## キャンセルされると補償が動かない

キャンセル済みのワークフロー context は、以降のアクティビティをスケジュールせずに即座に
失敗させます。つまり素直に書いた補償は、一番必要な場面で何もしない。

`Run` は `workflow.NewDisconnectedContext` から取った context で補償を回します。SDK 自身が
その doc コメントで示している対処です。

その context は外から誰もキャンセルできないので、`CompensationBudget` を必須にしました。
詰まったときに止める手段が他にないからです。各補償の `ScheduleToCloseTimeout` は残り予算に
切り詰められ、予算が尽きて実行されなかった補償は `CompensationReport.Skipped` に残ります。
黙って消えることはありません。

## タイムアウトしたステップが取り消されない

アクティビティがタイムアウトで失敗しても、ワーカー側では完走しているかもしれません。
結果を返せなかっただけ、という場合です。成功したときだけ補償を積む実装は、この副作用を
永久に取り残します。

`Step` は forward を実行する**前**に補償を登録します。代わりに、起きなかったステップに
対して補償が呼ばれることが起こります。だからアクティビティ側の契約が要ります。

## forward と補償が別のものを見てしまう

両者には同じ冪等キーが渡ります。キーは `RunID + "/" + ステップ名`。アクティビティの中では
`saga.IdempotencyKey` で読めます。

`FirstRunID` は使いません。あれは ContinueAsNew、Retry、Cron、Reset を跨いで保存される
ので、2回目の run が1回目のキーを再利用してしまう。全ステップが「適用済み」に見え、
課金せずに成功が返ります。連番でもありません。ステップを1つ挿入すると、以降のキーが
すべてずれるからです。

補償側の `ActivityID` には `:undo` が付きます。同じコマンド ID が2つあるとワークフロー
タスクが panic するためで、`IdempotencyKey` がこの接尾辞を剥がします。だから利用者からは
同じキーに見えます。

## エラーチェックを1つ忘れると、壊れた成功になる

ステップが失敗した後に body が nil を返しても、`Run` はワークフローを失敗させ、body の
戻り値を捨てます。これが無いと、副作用が半分だけ適用されたワークフローが完了として
記録される。UI は緑、アラートも鳴らない。

30行版にこの失敗は書けません。素の `if err != nil { return }` は、書き忘れれば次の行で
コンパイラかレビューに引っかかります。エラーハンドリングを省ける形にした以上、その穴は
ライブラリ側で塞ぐ必要がありました。

## 型で守れるものは型で守る

```go
func Step[In, Out any](ctx workflow.Context, s *Saga, name string,
    fwd  func(context.Context, In) (Out, error),
    undo func(context.Context, In) error,
    in In) (Out, error)
```

`fwd` と `undo` を SDK の `any` ではなく型付きの関数で受けるので、入れ替えや引数の型違いは
コンパイルエラーになります。`undo` は `error` だけを返すので、逆に書けば型が合いません。

SDK はここを見ていません。`ExecuteActivity` は関数値を検証の前に名前文字列へ変換し、
文字列経路では `validateFunctionArgs` が飛びます。引数の個数も型も、スケジュール時に
照合されない。取り違えが表に出るのはアクティビティが実行される時、補償なら saga が既に
失敗している最中です。

## 補償が失敗したとき

元のエラーは上書きしません。補償の失敗は `CompensationFailed` 型の
`temporal.ApplicationError` として返り、原因チェーンに元のエラーが残ります。失敗した
ステップ名は details に入ります。

`errors.Join` は使えません。Temporal の failure コンバータは具象型の型スイッチで、
`Unwrap() error` を1本だけ辿ります。join したエラーはどのケースにも当たらず、型名が
`joinError` になって原因チェーンが消え、`NonRetryableErrorTypes` の照合も効かなくなります。

既定では、1つ失敗しても残りの補償は続けます。返金の失敗を理由に在庫の解放まで
やめる理由はありません。`StopOnCompensationError` で変えられます。
