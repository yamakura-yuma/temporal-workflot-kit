在庫を押さえ、課金し、配送を手配する。どれかが失敗したら、そこまでに起きたことを 逆順で取り消す。他の4つはこの形からの派生です。

←

←

失敗した ship も補償されます。 補償はステップを実行する前に登録 されるからです。タイムアウトで失敗したアクティビティは、結果を返せなかっただけでワーカー上 では完走しているかもしれません。ship:undo は「何も予約されていない」と分かれば no-op で成功します。
## 失敗すると、失敗したステップを含めて逆順に取り消される * "ship" で失敗する注文 "rollback" * saga は "no carrier available" で失敗する * ステップ "reserve, charge, ship, ship:undo, charge:undo, reserve:undo" が実行された * 注文は "reserve, charge, ship" を保持していない

キャンセルされたとき

2. pipeline example/pipeline/ — 前段の出力が次段の入力になる

予約 ID を課金の入力に、課金 ID を配送の入力に渡します。見どころは補償の側です。

forward出力が次の入力になる

予約 IDres-chain↓
charge
課金 IDchg-res-chain↓
ship ✕
▼
補償forward と同じ入力を受け取る
reserve:undo
res-chain↑
charge:undo
chg-res-chain↑
ship:undo
補償は、そのステップ自身の出力を見られません。 登録されるのが実行より前 だからです。代わりに forward と同じ入力を受け取るので、前段までの出力は手元に あります。自分のステップの出力が要る場合は、冪等キーで引いてください。 
chg, _ := saga.Step(ctx, s, "charge", a.Charge, a.Refund,
    ChargeReq{Order: in, Reservation: res})   // ← 前段の出力

// Refund は同じ ChargeReq を受け取るので、req.Reservation が使える
## 前段の ID が、次段の補償にも渡っている * 連鎖する注文 "chain" を "ship" で失敗させる * 補償 "charge" が受け取った前段の ID は "res-chain" * 補償 "ship" が受け取った前段の ID は "chg-res-chain"

3. state example/state/ — Run の中を短く保つ

これだけは実行時の形ではなくコードの形の話です。アクティビティの入力が 増えると、ステップを並べただけのワークフローは読めなくなります。

Run の body2行
w := &fulfillment{in: in}return w.run(ctx, s)
→
fulfillment in / reservation / charge / shipment
▼ ステップはメソッド。state から入力を組み、結果を state に戻す
w.reserve→ w.reservation
→
w.chargeCardw.reservation を使う
→
w.shipw.charge を使う
func (w *fulfillment) run(ctx workflow.Context, s *saga.Saga) (Receipt, error) {
    w.reserve(ctx, s)
    w.chargeCard(ctx, s)
    w.ship(ctx, s)

    if err := s.Err(); err != nil {     // 分岐と戻り値の前に1回だけ見る
        return Receipt{}, err
    }
    return Receipt{...}, nil
}
state 構造体そのものを Step に渡すことはできません。 Step の入力はアクティビティの引数なので、シリアライズ可能である必要があります。 メソッドの中で state からリクエストを組んでください。

4. childflow example/childflow/ — ステップが子ワークフロー

ステップはアクティビティに限りません。梱包だけを子ワークフローにして、取り消しも子 ワークフローで行います。混在しても巻き戻しは1つの逆順です。

forward
reserveアクティビティ
→
packPackWorkflow（子）
→
ship ✕アクティビティ
▼ executor が違っても1つの逆順
補償
reserve:undo
←
pack:undoUnpackWorkflow（子）
←
ship:undo

executor ごとに違うのは3点だけ

実行冪等キーを載せる場所予算で切る対象
アクティビティ
saga.Step		 ExecuteActivity ActivityOptions.ActivityID ScheduleToCloseTimeout
子ワークフロー
saga.ChildStep		 ExecuteChildWorkflow ChildWorkflowOptions.WorkflowID WorkflowExecutionTimeout
ローカルアクティビティ
対象外		 ExecuteLocalActivity 無い ScheduleToCloseTimeout

どちらを呼ぶかは第1引数の型が選びます。context.Context なら アクティビティ、workflow.Context なら子ワークフロー。Temporal 自身の区別と 同じなので、名前ではなく型が教えてくれます。 

res,  _ := saga.Step(ctx, s, "reserve", a.Reserve, a.Unreserve, ReserveReq{Order: in})
pack, _ := saga.ChildStep(ctx, s, "pack", PackWorkflow, UnpackWorkflow, PackReq{Order: in})

// 子の側は自分の鍵を読む。":undo" は剥がされているので forward と同じ値
key, _ := saga.IdempotencyKeyOf(ctx)
## 子ワークフローのステップも逆順で取り消される * 子ワークフローを含む注文 "mixed" を "ship" で失敗させる * 子ワークフロー "pack, pack:undo" が起動された * 梱包と取り消しが見た冪等キーは一致する

5. approval example/approval/ — ステップの間で人を待つ

予約を取ってから承認を待ち、通れば課金します。結末が3つあり、どれも同じ経路で 巻き戻ります。ワークフロー本体はエラーを返すだけです。

reserve
→
承認待ちSelector
▼ 3つの結末
承認された→ charge → Receipt
却下されたApprovalDenied
時間切れタイマーが先に鳴る
待機中に Cancelcontext が閉じる
▼ 右の3つはどれも同じ
reserve:undo予約を解放する
if err := s.Err(); err != nil {   // 分岐の前に必ず見る
    return order.Receipt{}, err   // 失敗していれば res はゼロ値
}

decision, ok := awaitDecision(ctx, wait)
if !ok || !decision.Approved {
    // エラーを返すだけ。ロールバックは Run が引き受ける
    return order.Receipt{}, temporal.NewApplicationError("...", DeniedType, nil)
}
待っている間にキャンセルされても補償は走ります。 切り離した context で 実行されるからで、ワークフロー側は何も書きません。
