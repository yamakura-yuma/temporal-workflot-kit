# 仕様書

このディレクトリが、このライブラリの振る舞いの仕様書です。6 本の `.feature` は
日本語の Gherkin で書かれていて、**読み物であると同時に実行されます**。書いてある
ことが本当かどうかは `just spec` が確かめます。

実行する相手はインメモリのテスト環境ではなく、スイートがプロセス内に起動する実際の
Temporal dev server です。理由は `docs/development.md`「スイートが2つある理由」に
あります。

## 読む順

**`rollback.feature` から読んでください。** これが基本形で、残りの 5 本はその変種です。

| | 仕様 | 何の変種か |
| --- | --- | --- |
| 1 | [`rollback.feature`](rollback.feature) | **基本形。** アクティビティを順に実行し、失敗したら逆順で取り消す。成功・失敗・キャンセル・補償自体の失敗の4通り |
| 2 | [`state.feature`](state.feature) | 同じ振る舞いを、**書き方を変えて**も保てるか。5ステップの saga を構造体のメソッドに割った形と、素のまま並べた形の両方を動かして比べる |
| 3 | [`pipeline.feature`](pipeline.feature) | ステップの間に**データが流れる**とき。前段の出力が次段の入力になり、補償にも渡る |
| 4 | [`approval.feature`](approval.feature) | ステップが**アクティビティでない**とき その1。人の承認を待つ |
| 5 | [`childflow.feature`](childflow.feature) | ステップが**アクティビティでない**とき その2。子ワークフロー。しかも forward と取り消しで実行の仕方が違う |
| 6 | [`external.feature`](external.feature) | ステップが**アクティビティでない**とき その3。他のワークフローへの signal。冪等キーが載らない唯一の形 |

1 と 2 は「同じことを別の書き方で」、3 は「ステップの間のデータ」、4〜6 は
「ステップの実行のされ方」。この3つの軸で 6 本が並んでいます。

## 全部に共通する読み方

どの仕様も、**結果を見る**ステップの語彙は共通です。基本形で覚えれば残りは読めます。

| ステップ | 何を見ているか |
| --- | --- |
| `saga は成功する` / `saga は失敗する` / `saga は "..." で失敗する` | ワークフローの戻り値 |
| `アクティビティ "..." が実行された` | **ワークフロー履歴**。運用が Web UI で見る順序そのもの。名前は実際に走った関数（`Charge`、その補償は `Refund`） |
| `注文は "..." を保持したままである` / `保持していない` | ワークフロー履歴。そのアクティビティが完了し、かつ取り消す側（`Reserve` に対する `Unreserve`）が走っていないか |
| `補償に失敗したステップは "..."` | `CompensationReport` の報告。ここだけは**ステップ名**（`charge`）で、履歴の関数名とは別物 |
| `saga は運用者向けにフラグが立つ` | 検索属性。立てるのはライブラリではなくワークフロー（`example/workflow/order/`） |

**saga を起こすステップの語彙は仕様ごとに違います。** 子ワークフローの起動
（`childflow.feature`）、前段の ID（`pipeline.feature`）、在庫の確保数
（`external.feature`）など、そのテーマに固有のものは各ファイルにあります。

## 動かす

```bash
just spec            # 全部
just spec -run 'TestFeatures/成功した_saga_は何も取り消さない'   # 1 シナリオだけ
just spec-ui         # dev server を残す。落ちたシナリオの履歴を localhost:8233 で読む
```

ステップ文がどの Go 関数に繋がっているかは `specsteps/` にあります。対応づけの規則は
`docs/development.md`「仕様とコードの対応づけ」を読んでください。
